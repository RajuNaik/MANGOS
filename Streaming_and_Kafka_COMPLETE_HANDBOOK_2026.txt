1. WHY STREAMING GETS ITS OWN INTERVIEW TRACK
================================================================================

Batch data engineering has one clock: "did the job finish and is the output
correct." Streaming systems have two clocks running simultaneously — event
time (when something actually happened) and processing time (when the system
saw it) — and most of the hard interview questions live in the gap between
them: late data, out-of-order events, exactly-once under failure, and how to
keep unbounded state from growing forever. Interviewers use streaming
questions specifically to test whether a candidate reasons correctly about
partial failure and reprocessing, which is the core competency for any
production data platform, not just streaming systems.

2. KAFKA FUNDAMENTALS: TOPICS, PARTITIONS, BROKERS
================================================================================

TOPIC
  A named, durable, append-only log of records. Logically one stream of
  data (e.g., "orders," "clickstream-events"). Physically split into
  partitions for parallelism and scale.

PARTITION
  The unit of parallelism and ordering in Kafka. Each partition is an
  ordered, immutable sequence of records, each assigned a monotonically
  increasing offset. Kafka guarantees ORDER WITHIN A PARTITION ONLY — there
  is no cross-partition ordering guarantee for a topic. This single fact
  drives almost every "how do you guarantee ordering" interview question
  (Section 7).

BROKER
  A single Kafka server; a cluster is made of multiple brokers. Each
  partition is hosted on one broker as the leader, with replicas on other
  brokers as followers (Section 5). Brokers handle produce/consume requests
  for the partitions they lead.

RETENTION
  Kafka retains records for a configured period (time-based, e.g. 7 days)
  or size-based limit, REGARDLESS of whether consumers have read them —
  unlike a traditional message queue, Kafka doesn't delete a message once
  consumed. This is central to Kafka's role as a durable, replayable log
  (the "Kappa architecture" log referenced in the System Design handbook):
  multiple independent consumers can read the same topic at their own pace,
  and a consumer can replay from an earlier offset (or from the beginning)
  at any time within the retention window.

LOG COMPACTION (alternative retention strategy)
  Instead of (or in addition to) time-based deletion, log compaction
  retains only the LATEST record per key, deleting older records with the
  same key once compaction runs. This turns a Kafka topic into something
  closer to a changelog of "current state per key" — the mechanism behind
  Kafka Streams' state store changelog topics and a common pattern for a
  topic representing "latest known state of an entity" (e.g., current
  customer profile) rather than an event history.

3. KAFKA PRODUCERS DEEP DIVE
================================================================================

PARTITIONING STRATEGY
  - If a key is provided, the producer hashes the key to deterministically
    pick a partition — this is what guarantees all records for the same key
    (e.g., same user_id/session_id) land in the same partition and are
    therefore processed in order relative to each other.
  - If no key is provided, the default partitioner uses a sticky/round-
    robin strategy across partitions to balance load, but gives no ordering
    guarantee across records at all.

ACKS CONFIGURATION (the durability/latency tradeoff knob)
  acks=0: producer doesn't wait for any acknowledgment — fastest, no
    durability guarantee, records can be silently lost if the broker fails.
  acks=1: producer waits for the partition leader to acknowledge the write
    — good balance, but a record can still be lost if the leader fails
    before followers replicate it.
  acks=all (or -1): producer waits for the write to be acknowledged by all
    in-sync replicas (ISR, Section 5) — strongest durability, at the cost
    of higher latency. This is the answer whenever a design requires no
    data loss.

IDEMPOTENT PRODUCER
  enable.idempotence=true assigns each producer a unique ID and a
  monotonically increasing sequence number per partition, so the broker can
  detect and drop duplicate retries of the same message (e.g., from a
  network timeout where the write actually succeeded but the ack was lost,
  causing the producer to retry) — this converts "at-least-once with
  possible duplicates from retries" into effectively exactly-once AT THE
  PRODUCER-TO-BROKER hop specifically. It does not, by itself, give
  end-to-end exactly-once (that requires the full picture in Section 6).

TRANSACTIONAL PRODUCER
  Kafka transactions let a producer write to multiple partitions/topics
  atomically (all-or-nothing), and are the mechanism behind Kafka's
  "exactly-once" stream processing story when combined with a transactional
  consumer that only reads committed messages (read_committed isolation
  level) — this is what Kafka Streams uses internally for
  exactly-once-semantics (EOS) mode.

BATCHING & COMPRESSION
  Producers batch records (batch.size, linger.ms) before sending to
  improve throughput at a small latency cost — a classic throughput vs.
  latency tuning knob worth naming: increasing linger.ms lets more records
  accumulate into a batch, improving compression ratio and network
  efficiency, at the cost of added per-record latency. Compression
  (compression.type=snappy/lz4/zstd) reduces network and storage cost
  further, applied per-batch.

4. KAFKA CONSUMERS & CONSUMER GROUPS DEEP DIVE
================================================================================

CONSUMER GROUP
  A set of consumers that cooperatively read a topic, with Kafka
  automatically dividing the topic's partitions among the group's members
  — each partition is consumed by exactly ONE consumer within a given
  group at a time (this is how Kafka achieves parallel consumption while
  preserving per-partition ordering: one partition, one consumer, in
  order). Multiple DIFFERENT consumer groups can each independently
  consume the full topic at their own pace — this is how Kafka supports
  fan-out to multiple independent applications from one topic.

CONSUMER GROUP REBALANCING
  When a consumer joins/leaves a group (including crashing), Kafka
  triggers a rebalance, reassigning partitions among the remaining/new
  consumers. Rebalances pause consumption briefly and are a common source
  of latency spikes in production Kafka consumers — knowing this is a
  strong signal in an interview ("why did our consumer lag spike when we
  deployed a new consumer instance" -> rebalance pause, plus cold state if
  stateful).

OFFSET MANAGEMENT
  Consumers track their position in each partition via an offset, committed
  back to Kafka (in an internal __consumer_offsets topic) either
  automatically (enable.auto.commit=true, on a timer — risks reprocessing
  or skipping records on crash depending on exact timing) or manually
  (commit after successfully processing/writing output — the correct
  pattern for any pipeline that needs precise delivery guarantees, since it
  lets you commit the offset ONLY after the corresponding output write has
  succeeded, which is the foundation of exactly-once processing pipelines).

CONSUMER LAG
  The difference between the latest offset produced to a partition and the
  offset the consumer has committed — the single most important streaming
  pipeline health metric. Rising lag means the consumer can't keep up with
  the producer rate; this is the first thing to check when a streaming
  pipeline's freshness SLA is being missed, and the primary signal driving
  autoscaling decisions for consumer instances.

5. KAFKA REPLICATION, DURABILITY, AND ISR
================================================================================

REPLICATION FACTOR
  Each partition has N replicas (typically 3 in production) spread across
  different brokers for fault tolerance — one is the LEADER (handles all
  reads/writes for that partition), the rest are FOLLOWERS that replicate
  the leader's log.

IN-SYNC REPLICAS (ISR)
  The set of replicas that are fully caught up with the leader within a
  configured lag threshold. Only ISR members are eligible to be elected
  leader if the current leader fails, which is what prevents data loss on
  failover — this is exactly why acks=all specifically means "wait for all
  ISR members to acknowledge," not "wait for all replicas" (a lagging
  replica outside the ISR isn't in the acknowledgment path).

MIN.INSYNC.REPLICAS
  A broker-side/topic-side setting that, combined with acks=all, defines
  the minimum durability guarantee: if fewer than min.insync.replicas are
  in the ISR, the broker rejects writes rather than accepting them with
  weaker durability — the standard production combination for critical
  data is replication.factor=3, min.insync.replicas=2, acks=all, which
  tolerates one broker failure with zero data loss and zero write
  rejection, while still rejecting writes if two brokers are down
  (protecting against writes with no real redundancy).

LEADER ELECTION ON FAILURE
  If the leader broker fails, Kafka (via the controller, itself elected
  among brokers, using KRaft consensus in modern Kafka versions that have
  removed the old ZooKeeper dependency) promotes an ISR replica to leader —
  worth mentioning that Kafka's architecture has moved to KRaft-based
  self-managed metadata/consensus, removing the historical ZooKeeper
  dependency, if asked about Kafka's own internal architecture.

6. DELIVERY SEMANTICS: AT-MOST-ONCE, AT-LEAST-ONCE, EXACTLY-ONCE
================================================================================

This section is the single most commonly probed streaming topic in MAANG
interviews. Know it precisely, at every hop of the pipeline (producer ->
broker, broker -> consumer, consumer -> sink).

AT-MOST-ONCE
  A record might be lost, but never processed twice. Happens when a
  producer doesn't retry on failure (acks=0 or no retry logic), or a
  consumer commits its offset BEFORE processing the record (so a crash
  after commit but before processing loses that record). Rarely the
  correct design choice; occasionally acceptable for non-critical
  telemetry where losing a sample is fine but duplicate-processing side
  effects (e.g., double-charging) are not.

AT-LEAST-ONCE
  A record is never lost, but might be processed more than once. This is
  Kafka's default practical behavior in most real pipelines: producer
  retries on failure (possibly creating duplicates if the write actually
  succeeded but the ack was lost — mitigated by the idempotent producer,
  Section 3), and a consumer that commits its offset AFTER processing (so
  a crash after processing but before commit causes the record to be
  reprocessed on restart). This is the standard, recommended default
  unless you have a specific reason to invest in stronger guarantees.

EXACTLY-ONCE (end-to-end)
  Achieved NOT by magically preventing duplicates from ever occurring, but
  by combining at-least-once delivery with IDEMPOTENT PROCESSING at the
  sink, so that reprocessing a duplicate has no additional effect. Two
  concrete mechanisms:
    1. Idempotent sink writes: MERGE/upsert keyed on a natural or
       deterministic ID (e.g., Kafka partition+offset, or a business key)
       so replaying the same record twice produces the same end state as
       processing it once (this is exactly the pattern used in Delta Lake
       MERGE-based CDC ingestion covered in the System Design handbook).
    2. Atomic offset-commit-with-output-write: Spark Structured Streaming's
       checkpointing ties the commit of "which offsets have been
       processed" to the commit of the output write itself (via the
       checkpoint's write-ahead log and, for supported sinks, transactional
       writes) — so on restart after failure, Spark reprocesses exactly the
       micro-batch that didn't fully commit, and because the sink write is
       idempotent (Delta MERGE, or a sink written with foreachBatch logic
       that dedupes), reprocessing that batch is safe.
  Kafka's own native EOS (transactional producer + read_committed consumer,
  used internally by Kafka Streams) extends this guarantee natively within
  the Kafka ecosystem (produce -> process -> produce, all within one
  Kafka transaction) but does NOT automatically cover an external sink
  (a database, a Delta table) unless that sink's write is also made
  idempotent/transactional as part of the same logical commit — a strong,
  precise interview point: "exactly-once is only as end-to-end as your
  weakest, non-idempotent hop."

7. ORDERING GUARANTEES AND PARTITIONING STRATEGY
================================================================================

THE CORE RULE
  Kafka guarantees order only within a single partition, for records
  produced by a single producer (in the absence of retries reordering
  things without idempotence enabled). There is no ordering guarantee
  across partitions.

DESIGNING FOR ORDERING
  If a design requires "all events for user X processed in order," the key
  used for partitioning MUST be user X's identifier — this guarantees
  those events land in the same partition and are read by the same
  consumer instance in produce order. This is why session-keyed clickstream
  design (System Design handbook, Problem 2) explicitly partitions by
  session_id: correctness of sessionization depends on it.

TRADEOFF: PARTITION COUNT vs. ORDERING GRANULARITY
  More partitions = more parallelism = higher throughput, but ordering is
  only preserved WITHIN a partition, so the finest ordering guarantee you
  can offer is "ordered per partition key," never "globally ordered
  across the whole topic" without collapsing to a single partition (which
  kills parallelism). This is a real, unavoidable tradeoff to state
  explicitly rather than something to "solve" — a mature answer says
  "we don't need global ordering, we need per-entity ordering, so we
  partition by entity key and accept no cross-entity ordering guarantee."

HOT PARTITION / SKEWED KEY PROBLEM
  If one key (e.g., one viral user session, one huge retail store) produces
  disproportionate volume, its partition becomes a bottleneck (same
  skew problem as Spark shuffle skew, Spark Internals handbook Section 7,
  but at the Kafka layer). Mitigations: composite keys (key + a bounded
  random suffix) when strict per-key ordering isn't actually required at
  fine granularity, increasing partition count with a partitioner aware of
  key cardinality, or isolating known-hot keys to dedicated partitions/
  topics.

8. SCHEMA MANAGEMENT (SCHEMA REGISTRY, AVRO/PROTOBUF/JSON)
================================================================================

WHY A SCHEMA REGISTRY
  Kafka itself is schema-agnostic — it stores bytes. Without a shared
  contract, producers and consumers can silently drift out of sync on
  field types/names, breaking consumers at runtime. A Schema Registry
  (Confluent Schema Registry, AWS Glue Schema Registry) stores versioned
  schemas centrally; producers/consumers reference a schema ID embedded in
  each message rather than the full schema, and the registry enforces
  compatibility rules on schema evolution.

FORMAT CHOICES
  Avro: compact binary, schema embedded/referenced via registry, strong
    tooling in the Kafka ecosystem, the traditional default choice.
  Protobuf: also compact binary, strong typing, increasingly common
    especially where the same schema definitions are shared with gRPC
    services.
  JSON (with or without JSON Schema in the registry): human-readable,
    larger payload size, easier to debug ad hoc but weaker built-in schema
    enforcement unless paired with JSON Schema validation.

COMPATIBILITY MODES (the actual interview-testable content)
  BACKWARD: a new schema can read data written with the OLD schema — safe
    to add fields with defaults, or remove optional fields. Consumers
    upgrade first is safe.
  FORWARD: OLD schema can read data written with the NEW schema — safe to
    add fields (consumers ignore unknown fields), unsafe to remove
    required fields. Producers upgrade first is safe.
  FULL: both backward and forward compatible simultaneously — the
    safest, most restrictive option, generally the recommended default for
    shared topics with many independent consumer teams, since it removes
    the need to coordinate deployment order between producers and
    consumers.
  NONE: no compatibility enforcement — schema can change arbitrarily;
    high risk, generally only acceptable for early-stage/internal topics
    with a single producer and consumer under the same team's control.

PRACTICAL PATTERN
  Always add new fields as optional with a default value, never repurpose
  or remove a field consumers depend on without a coordinated, versioned
  migration — this single practice avoids the vast majority of real-world
  schema-evolution incidents and is a strong, concrete answer to "how do
  you evolve a schema safely in a live streaming pipeline."

9. SPARK STRUCTURED STREAMING WITH KAFKA (PRACTICAL PATTERNS)
================================================================================

BASIC READ
  spark.readStream.format("kafka").option("kafka.bootstrap.servers", ...).
  option("subscribe", "topic_name").option("startingOffsets", "latest").
  load() — returns a DataFrame with key/value (binary), topic, partition,
  offset, timestamp columns. The value column must be explicitly
  deserialized (from_avro/from_json against the known schema, ideally
  fetched from the Schema Registry) since Kafka payloads are opaque bytes
  to Spark.

STARTINGOFFSETS SEMANTICS
  "latest": only new records from the moment the query starts (used for a
    fresh streaming query where historical data isn't needed).
  "earliest": replay the entire retained topic history (used for backfills
    or a brand-new consumer that needs full history within retention).
  Once a checkpoint exists, startingOffsets is IGNORED on restart — Spark
  always resumes from the checkpointed offsets, which is the correct and
  expected exactly-once-supporting behavior; this trips people up in
  interviews and in practice ("why didn't changing startingOffsets do
  anything" -> because a checkpoint already exists).

FOREACHBATCH — the idiomatic pattern for arbitrary/idempotent sinks
  writeStream.foreachBatch(lambda batch_df, batch_id: ...) lets you treat
  each micro-batch as a regular (batch) DataFrame and apply arbitrary
  logic — most commonly a Delta MERGE keyed on a business/dedup key, which
  is exactly how idempotent, exactly-once-effective sinks are implemented
  in practice for sinks that don't have native streaming-sink support
  (most databases, most REST APIs). This is the pattern to describe when
  asked "how do you write Kafka streaming data into a table with upserts."

TRIGGER.AVAILABLENOW FOR COST-EFFICIENT "STREAMING"
  As covered in the Spark Internals handbook Section 14, running a
  Structured Streaming query with Trigger.AvailableNow on a schedule
  (e.g., an hourly Databricks Job) processes all currently-available Kafka
  data as one or more batches then stops, giving checkpoint-based
  exactly-once-supporting correctness without paying for an always-on
  cluster — the standard 2026 answer for "near-real-time but cost-
  sensitive" requirements (roughly the 1-15 minute SLA band from the
  System Design handbook's batch/streaming decision tree).

10. WINDOWING, WATERMARKING, AND LATE DATA — DEEP DIVE
================================================================================

TUMBLING WINDOWS
  Fixed-size, non-overlapping windows (e.g., 5-minute buckets: [0:00-0:05),
  [0:05-0:10)...). Each event belongs to exactly one window based on its
  event_time. Standard choice for simple periodic aggregates ("events per
  5 minutes").

SLIDING WINDOWS
  Fixed-size windows that overlap, advancing by a slide interval smaller
  than the window size (e.g., a 10-minute window sliding every 5 minutes,
  so windows are [0:00-0:10), [0:05-0:15)...). Each event can belong to
  MULTIPLE windows — used for smoothed/rolling metrics (e.g., "rolling
  10-minute average, updated every 5 minutes").

SESSION WINDOWS
  Dynamic-length windows that close after a gap of inactivity (e.g., "end
  the session after 30 minutes with no events for this user") — used for
  clickstream sessionization (System Design handbook, Problem 2). Unlike
  tumbling/sliding, session window boundaries are DATA-DEPENDENT, not
  fixed on the clock.

WATERMARKING MECHANICS (expanding on Spark Internals Section 14)
  withWatermark("event_time", "10 minutes") declares: "once the maximum
  event_time seen so far advances past a window's end + 10 minutes, that
  window is considered final; state for it can be dropped, and any further
  events for it are treated as too late." This is a per-key-independent,
  monotonic-in-max-event-time mechanism — it does NOT pause for a
  specific key falling behind; it advances based on the fastest-moving
  data seen. Understand this precisely: watermarking bounds STATE SIZE and
  defines a firm cutoff, at the cost of definitionally dropping/misrouting
  sufficiently late data — there is no watermark setting that guarantees
  both bounded state AND zero dropped late data; it is an explicit,
  named tradeoff to state as such in an interview, not a knob to "tune
  away."

HANDLING VERY LATE DATA THAT MUST NOT BE DROPPED
  If correctness genuinely requires incorporating data arriving hours or
  days late (which a bounded watermark can't accommodate without keeping
  huge state), the standard pattern is a SEPARATE CORRECTION/BACKFILL
  PATH: the streaming pipeline handles the common case within the
  watermark bound, and a periodic batch reconciliation job re-aggregates
  from the raw bronze/log data for any window that received corrections,
  overwriting the previously-published (approximate) result — this is
  effectively a mini Lambda architecture layered on top of a Kappa-style
  stream, and a genuinely strong answer to "what if the watermark isn't
  enough."

11. STREAM-STREAM AND STREAM-STATIC JOINS
================================================================================

STREAM-STATIC JOIN
  Joining a streaming DataFrame to a static (batch-read, e.g. a dimension
  table) DataFrame — straightforward, no additional state management
  beyond normal micro-batch processing, since the static side doesn't
  change within a micro-batch (though it CAN be refreshed between batches
  by re-reading the source, depending on the API/version used).

STREAM-STREAM JOIN
  Joining two streaming DataFrames (e.g., "ad impressions" stream joined
  to "ad clicks" stream to compute click-through attribution) requires
  BUFFERING state from both sides, because a matching record on either
  side might arrive at any time — Spark must keep enough historical state
  from both streams to match against future arrivals from the other side.
  This is why stream-stream joins REQUIRE watermarks on both sides (plus
  optionally a time-range join condition, e.g. "click must occur within 1
  hour of impression") — without a watermark, Spark would have to retain
  state for every record from both sides FOREVER, since a match could
  theoretically arrive at any future time. The watermark + time-range
  condition together bound how long state must be retained before Spark
  can safely conclude "no match will ever arrive" and evict that state.

INTERVIEW FRAMING
  "Stream-stream joins are stateful joins with an unbounded matching
  window unless you bound it explicitly — watermarks and time-range join
  conditions aren't just a performance optimization here, they're what
  makes the join operationally possible at all, since without them state
  would grow without bound."

12. KAFKA CONNECT & CDC PATTERNS
================================================================================

KAFKA CONNECT
  A framework for running reusable, configuration-driven connectors that
  move data into (source connectors) or out of (sink connectors) Kafka,
  without writing custom producer/consumer code — runs as a distributed,
  fault-tolerant cluster of workers, with connector state/offsets tracked
  in internal Kafka topics (so Connect itself relies on Kafka's durability
  guarantees for its own operation).

DEBEZIUM (the standard CDC source connector)
  Reads a database's write-ahead log (WAL for Postgres, binlog for
  MySQL) directly rather than polling with SQL queries — this is log-based
  CDC (referenced in the System Design handbook, Problem 3), and it's the
  correct answer whenever an interview asks "how do you capture changes
  from a database without querying it repeatedly": log-based CDC adds
  effectively zero query load to the source database, captures deletes
  (which a "SELECT WHERE updated_at > last_run" polling approach cannot,
  since a deleted row simply isn't there to select), and preserves exact
  operation order from the source's transaction log.

DEBEZIUM EVENT STRUCTURE
  Each CDC event carries a "before" image, an "after" image, and an
  operation type (c=create, u=update, d=delete, r=read/snapshot) — a
  downstream consumer (Spark/Kafka Streams) uses the operation type to
  decide whether to INSERT, UPDATE (MERGE), or soft/hard-DELETE in the
  target system, exactly matching the silver-layer MERGE logic described
  in the System Design handbook's CDC pipeline problem.

SNAPSHOT + INCREMENTAL PATTERN
  Debezium (and CDC generally) typically starts with an initial full
  snapshot of the source table's current state, then switches seamlessly
  to continuous incremental log-tailing — a design detail worth
  mentioning explicitly when asked "how do you bootstrap a CDC pipeline
  for a table that already has years of existing data."

13. KAFKA STREAMS / KSQLDB vs. SPARK/FLINK — WHEN TO USE WHAT
================================================================================

KAFKA STREAMS
  A Java/Scala LIBRARY (not a separate cluster/framework to deploy) that
  runs embedded within your own application, reading from and writing to
  Kafka topics, with built-in support for exactly-once semantics, local
  state stores (RocksDB-backed, same idea as Spark's state store), and
  windowed aggregations. Best fit: lightweight, per-service stream
  processing embedded directly in a microservice, where you don't want to
  stand up and operate a separate Spark/Flink cluster just for one
  service's stream logic.

KSQLDB
  A SQL layer on top of Kafka Streams, letting you express streaming
  transformations/aggregations declaratively without writing Java/Scala —
  good for simpler streaming ETL and for teams that are SQL-first and want
  to avoid standing up a full Spark/Flink job for straightforward
  filter/aggregate/join pipelines directly between Kafka topics.

SPARK STRUCTURED STREAMING
  Best fit when the streaming pipeline needs to interoperate heavily with
  batch processing and the broader lakehouse (writing to Delta, joining
  against large static dimension tables, sharing code/logic with batch
  jobs) — the natural choice in a Databricks-centric or lakehouse-centric
  organization, and the right default answer for most DE-focused (as
  opposed to pure low-latency microservice) interview scenarios given your
  Databricks background.

FLINK
  Best fit for the lowest-latency, most complex stateful stream processing
  (true event-at-a-time processing rather than micro-batch, sophisticated
  CEP pattern matching, very large/long-lived state with fine-grained
  control) — the choice when sub-second latency genuinely matters (fraud
  detection, real-time bidding) and the operational complexity of running
  a dedicated Flink cluster is justified by the latency requirement.

DECISION SUMMARY
  Embedded in one microservice, simple logic       -> Kafka Streams/ksqlDB
  Lakehouse-integrated, mixed batch+streaming       -> Spark Structured
                                                        Streaming
  Lowest latency, complex CEP, heavy state           -> Flink

14. FLINK vs. SPARK STRUCTURED STREAMING
================================================================================

EXECUTION MODEL
  Flink: true streaming, event-at-a-time (or micro-batched internally only
    as an implementation detail, not exposed as the programming model) —
    native low latency without a trigger-interval tradeoff.
  Spark Structured Streaming: micro-batch by default (Spark Internals
    handbook Section 14) — latency bounded below by the trigger interval,
    though Trigger.AvailableNow and (experimental) Continuous Processing
    mode push toward the batch and low-latency extremes respectively.

STATE MANAGEMENT
  Both support large state via RocksDB-backed state stores with
  checkpointing to durable storage. Flink's state management is generally
  considered more mature/flexible for very complex, long-lived stateful
  applications (e.g., arbitrary custom state with fine-grained TTL
  control via the ProcessFunction API), while Spark's stateful streaming
  API is comparatively higher-level (built around windowed
  aggregations/joins primarily) but easier to reason about within the same
  codebase as batch jobs.

ECOSYSTEM FIT
  Spark's advantage in a DE-heavy, lakehouse-centric shop is sharing one
  engine, one set of skills, and one codebase style across batch and
  streaming, plus native, first-class Delta Lake integration. Flink's
  advantage is when streaming IS the primary workload (not a lakehouse
  ingestion detail) and true low-latency, complex event processing is a
  core product requirement.

INTERVIEW FRAMING
  "I'd default to Spark Structured Streaming in a lakehouse-centric org
  because it shares the same engine, catalog, and codebase as our batch
  pipelines, and Trigger.AvailableNow covers most near-real-time SLAs
  cost-effectively. I'd reach for Flink specifically when the SLA is
  sub-second and/or the logic requires genuine complex event processing
  that doesn't map cleanly onto windowed DataFrame operations."

15. OPERATIONAL CONCERNS: MONITORING, SCALING, FAILURE RECOVERY
================================================================================

KEY METRICS TO MONITOR
  - Consumer lag (per partition, and aggregated) — the primary freshness/
    health signal.
  - Under-replicated partitions — signals broker/replication issues before
    they become data-loss risk.
  - Request/response latency percentiles (p50/p95/p99) at the broker.
  - For Spark Structured Streaming: batch processing time vs. trigger
    interval (if processing time consistently exceeds the trigger
    interval, the query is falling behind — visible directly in the
    Structured Streaming UI/metrics).
  - State store size growth (unbounded growth signals a missing/too-loose
    watermark).

SCALING CONSUMERS
  Consumer group parallelism is capped by partition count — you cannot
  usefully run more consumer instances in a group than there are
  partitions (extra consumers sit idle). Scaling a Kafka-backed pipeline
  beyond current partition count requires increasing partition count on
  the topic, which is a one-way operation for existing topics in terms of
  its effect on key-to-partition mapping (adding partitions to an existing
  topic changes the hash-partitioning result for keys going forward,
  which can break "same key always same partition" assumptions for
  existing unprocessed data spanning the change) — worth flagging as an
  operational gotcha: partition count is usually planned upfront with
  headroom, rather than casually increased later.

FAILURE RECOVERY PATTERNS
  - Broker failure: handled transparently via ISR leader election
    (Section 5), assuming replication factor > 1 — clients reconnect to
    the new leader automatically.
  - Consumer crash: handled via consumer group rebalance + resuming from
    last committed offset (at-least-once, unless idempotent processing is
    in place for exactly-once-effective behavior).
  - Spark Structured Streaming query failure: restart resumes from
    checkpoint (Spark Internals handbook Section 14); the checkpoint must
    be on durable, shared storage (not local disk) to survive the
    restart happening on a different node/cluster.

DISASTER RECOVERY / MULTI-REGION
  MirrorMaker 2 (or cloud-native equivalents like Confluent Cluster
  Linking, or Kinesis/Event Hubs cross-region replication) replicates
  topics across Kafka clusters in different regions for DR — worth naming
  if asked about multi-region streaming architecture, alongside the
  standard caveat that cross-region replication is itself asynchronous
  and introduces its own lag/consistency considerations.

16. COMMON DESIGN PROBLEMS (WORKED EXAMPLES)
================================================================================

--------------------------------------------------------------------------------
PROBLEM A: Design an exactly-once pipeline from Kafka to a Delta table
--------------------------------------------------------------------------------
  Kafka topic (orders, keyed by order_id) -> Spark Structured Streaming
  readStream -> deserialize via Schema Registry -> foreachBatch ->
  Delta MERGE keyed on order_id (idempotent upsert) -> checkpoint on S3/
  ADLS (durable, shared storage).
  Why this achieves exactly-once-effective semantics: Spark's checkpoint
  ties offset commit to the completion of the foreachBatch call; if the
  job crashes mid-batch and restarts, it reprocesses that exact batch, but
  the Delta MERGE on order_id makes reprocessing idempotent — the end
  state is identical whether the batch ran once or was retried.

--------------------------------------------------------------------------------
PROBLEM B: Design a topic/partitioning scheme for a multi-tenant event
platform where per-tenant ordering matters but tenants vary hugely in size
--------------------------------------------------------------------------------
  Partition key = tenant_id for small/medium tenants (guarantees per-
  tenant ordering, and Kafka's hash partitioner spreads many small tenants
  across partitions reasonably evenly). For a small number of very large
  tenants that would otherwise create a hot partition, give each large
  tenant its OWN dedicated topic (or a dedicated partition range via a
  custom partitioner), isolating their volume from smaller tenants and
  allowing independent scaling — directly mirrors the "bridge model"
  isolation strategy from the System Design handbook's multi-tenant
  problem, applied at the Kafka layer specifically.

--------------------------------------------------------------------------------
PROBLEM C: A downstream consumer needs strictly-ordered, exactly-once
delivery of financial transaction events with zero tolerance for data loss
--------------------------------------------------------------------------------
  Producer: acks=all, enable.idempotence=true, key by account_id (ensures
  ordering per account). Topic: replication.factor=3,
  min.insync.replicas=2. Consumer: manual offset commit AFTER a
  successful, idempotent write to the sink (upsert keyed on a transaction
  ID, not blind append) — combining broker-level durability (acks=all +
  ISR) with consumer-side idempotent processing to close the loop
  end-to-end, exactly the "at-least-once delivery + idempotent processing"
  formula from Section 6, applied to the highest-stakes case (financial
  data) to justify every individual setting explicitly.

17. INTERVIEW QUESTION BANK WITH MODEL ANSWERS
================================================================================

Q: "How does Kafka guarantee message ordering?"
A: "Only within a single partition — records within one partition are
   strictly ordered by offset. There's no ordering guarantee across
   partitions. So if a use case needs ordered processing per entity (per
   user, per account), you partition by that entity's key, which
   guarantees all its events land in the same partition and are consumed
   in order by whichever single consumer owns that partition within the
   group."

Q: "What's the difference between at-least-once and exactly-once, and how
   do you actually achieve exactly-once in practice?"
A: "At-least-once means no data loss but possible duplicate processing.
   True exactly-once isn't usually achieved by preventing duplicates from
   ever occurring — it's achieved by combining at-least-once delivery
   with idempotent processing at the sink, so reprocessing a duplicate is
   a no-op. Concretely: commit consumer offsets only after the output
   write succeeds, and make that output write idempotent — an upsert
   keyed on a business ID rather than a blind insert — so replaying the
   same record twice leaves the same end state."

Q: "Why do stream-stream joins require watermarks?"
A: "Because either side of the join could theoretically match a future
   record from the other side at any point, Spark has to retain state
   from both sides indefinitely without a bound. A watermark plus a
   time-range join condition tells Spark 'a match can only arrive within
   this window,' which lets it safely evict state for records outside
   that window — without it, state would grow unbounded and the job would
   eventually fail."

Q: "How would you evolve a Kafka topic's schema without breaking existing
   consumers?"
A: "Register the new schema with the Schema Registry under FULL
   compatibility mode if possible — meaning the change must be both
   backward and forward compatible. Practically that means adding new
   fields as optional with defaults and never removing or repurposing a
   field existing consumers rely on. That way producers and consumers can
   deploy independently, in either order, without coordination."

Q: "Consumer lag is climbing steadily on a topic. Walk me through your
   diagnosis."
A: "First check whether it's a throughput problem (consumer processing
   rate below producer rate) or a stuck/crashed consumer instance
   (frequent rebalances, or one partition's consumer dead). If it's
   throughput, check whether consumer count is already at partition count
   — if so, I need more partitions, not more consumers, since parallelism
   is capped by partition count. I'd also check for skew — one partition
   with disproportionate volume can lag even while others are fine, same
   root cause as Spark shuffle skew but at the Kafka layer."

Q: "Why would you choose Kafka Streams over Spark Structured Streaming for
   a given use case?"
A: "Kafka Streams is a library, not a cluster to operate — it runs
   embedded in your own application. For a single microservice doing
   fairly simple stream transformations directly between Kafka topics,
   standing up a whole Spark job/cluster is overkill; Kafka Streams (or
   ksqlDB for a SQL-first team) keeps the operational footprint smaller.
   I'd reach for Spark when the pipeline needs to interoperate with batch
   jobs and the lakehouse, sharing code and writing to Delta directly."

18. QUICK-REFERENCE CHEAT SHEET
================================================================================

KAFKA CORE GUARANTEES
  Ordering: within a partition only, never across partitions
  Durability (strongest): replication.factor=3, min.insync.replicas=2,
    acks=all
  Retention: time/size-based, independent of consumption; log compaction
    for "latest value per key" topics

DELIVERY SEMANTICS FORMULA
  At-most-once  = no retry / commit-before-process (data loss risk)
  At-least-once = retry + commit-after-process (default recommended)
  Exactly-once  = at-least-once delivery + idempotent sink write (MERGE/
                  upsert keyed on business ID)

PRODUCER DURABILITY KNOBS
  acks=0    -> fire and forget, fastest, least safe
  acks=1    -> leader ack only
  acks=all  -> full ISR ack, strongest durability
  enable.idempotence=true -> dedupes retry-caused duplicates at the broker

SCHEMA COMPATIBILITY MODES
  BACKWARD -> new schema reads old data (consumers upgrade first)
  FORWARD  -> old schema reads new data (producers upgrade first)
  FULL     -> both (safest default for multi-team shared topics)
  NONE     -> no enforcement (high risk)

WINDOW TYPES
  Tumbling -> fixed, non-overlapping, one window per event
  Sliding  -> fixed, overlapping, event can be in multiple windows
  Session  -> dynamic length, closes after inactivity gap, data-dependent

WATERMARK, ONE-LINE DEFINITION
  "State for a window is dropped once max event_time seen so far passes
  window_end + allowed_lateness — bounds state size, at the cost of
  definitionally dropping sufficiently late data."

STREAM-STREAM JOIN REQUIREMENT
  Requires watermark + time-range join condition on BOTH sides, or state
  grows unbounded.

TOOL SELECTION
  Embedded/single-service, simple logic     -> Kafka Streams / ksqlDB
  Lakehouse-integrated, mixed batch+stream   -> Spark Structured Streaming
  Sub-second, complex CEP, heavy state       -> Flink

TOP HEALTH METRIC
  Consumer lag (per partition + aggregate) — the first thing to check for
  any "pipeline is behind" question.
